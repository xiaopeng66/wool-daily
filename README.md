# wool-daily — 每日羊毛推荐表

每天 **9/15/21 点**自动抓取全网羊毛线索，生成一份**推荐表（HTML）**发布到
GitHub Pages（<https://xiaopeng66.github.io/wool-daily/>），**QQ 推一条文本**：链接 + 本轮条数。
只做推荐，不写单篇稿；写稿仍然是人工（或 baipiao-daily skill）的事。

**题材口径（2026-10-24 定）：只做科技**——AI 额度、软件/游戏限免、云资源与域名建站、
数码硬件资讯。吃的、生活用品、服饰美妆、家电、购物券/满减/年卡充值一律不发；
VPS/主机、梯子/机场、AI 中转站也不发。

## 产出

| 文件 | 说明 |
|---|---|
| `out/YYYY-MM-DD.html` | 推荐表（自包含，手机/电脑都能直接打开） |
| `index.html`（仓库根） | **线上最新一期**，`run-daily.sh` 每轮从 `out/` 复制 |
| `YYYY-MM-DD.html`（仓库根） | 当日归档，与 `index.html` 同源 |
| `data/YYYY-MM-DD.json` | 结构化结果（给后续流程/LLM 用） |
| `data/last-brief.txt` | 给 agent 的 TOP 8 简报（每次覆盖） |
| `data/last-round.json` | 上一轮推送的条目快照（「本次新增」的判据） |
| `data/seen.json` | 台账：每条线索首次展示日 `first_seen_day`（「往期未选」的判据） |

PDF 默认**不生成**（`--no-pdf`）；需要时手动跑 `python3 wool_daily.py --date YYYY-MM-DD`。
注意：`--date` 跑**历史日期**时不会覆盖已有归档，会自动另存为 `<日期>-rerun<时间>`
（要覆盖原件加 `--force-overwrite`）。

## 页面怎么读

界面沿用 AI 福利站（linuxsb-daily）的设计语言：靛蓝主色、16px 圆角卡片、
sticky 顶栏、分组标题带分隔线、深浅两套主题。v2（2026-10-24 改版）：

- **统计带**：顶部四格——条可写 / 条已排除 / 条线索（去重后）/ 来源在线（6/6）。
- **搜索 + 筛选**：顶部可按标题/摘要/标签关键词搜索；类别 chips 带条数；排序支持
  「分数优先 / 最新发布」。全部在前端完成，页面仍是单文件、零外部依赖。
- **今日优先**：分数 ≥55 取前 8；不足 6 条时按分数 Top 8 兜底，**组头口径如实标注**
  （如「分数 Top 8（≥55 分的只有 2 条）」，不再硬写 ≥55）。
- **卡片结构固定五层、同行等高对齐**：顶行（类目徽章 + 确定性 + 分数）→ 标题 →
  标签 → 摘要（3 行截断）→ 底部（来源 · 时间 · 打开原帖按钮 · 明文 URL，钉在同一水平线）。
- **分数构成徽章**：每张卡摘要下方一行绿/红小徽章（`+25 免费可领`、`−12 限地区`），
  分数怎么来的一眼可见；搜索也覆盖这些关键词。
- **标签**：`本次新增`（靛蓝加粗）= **这一轮推送才有、上一轮没有的**——每天推 3 次，
  最想看的就是这个；`今日首见`（淡蓝）= 今天第一次进榜但上一轮已在；`在榜续留`（灰）=
  上一轮就有的旧条目。绿色=加分项（免费可领/永久/官方域名）；
  黄色=**有门槛**（限地区/限银行卡/限运营商/付费前置/满减）；红色=**有风险**（含推广/概率性）。
  「本次新增」的卡片左侧还有一道绿线，长列表滚动时不用逐张看标签。
- **分类清单**：AI 额度 / 云资源 / 域名建站 / 其他（生活羊毛类已随「只做科技」停发；
  VPS/主机类整体排除，不进清单），已在优先区出现的不重复（组头注明「另有 N 条在今日优先」）。
- **折叠区**：「说明 · 分数怎么来的 · 排除规则」；「已排除 N 条」按原因分组、
  每条带原帖链接（点开核对是否误杀），单组最多列 12 条。非科技条目按细分归因
  （`非科技·吃的`/`生活用品`/`服饰美妆`/`家电`/`购物券`/`影音会员`/`科技资讯`/`无科技特征`）。
- **其他**：右上角深浅主题切换（记住选择）、右下角返回顶部。

QQ 里只收到一条：`🐑 羊毛日报已更新（日期 时间）` + `本次新增 N 条 · 在榜 N 条` +
带 `?v=` 时间戳的站点链接（绕 CDN 缓存，点开就是新版）。不再发 HTML 附件、不再有 AI 点评。

**「本次新增」怎么判定**：每轮生成后会存一份条目快照（`data/last-round.json`），
下一轮拿本轮条目和它对比，不在快照里的就是本轮新增。所以：
- 同一天 9/15/21 三轮，每轮的「本次新增」= 相对上一轮的增量；
- 首次部署/快照丢失时，全部条目按「本次新增」处理（宁可标多，不漏标）。

页面顶部眉标和页脚显示的是**本期实际生成时间**（`本题生成于 …`），不是固定的「每天 20:00」——
每轮推送都会刷新，看一眼就知道手上这版是不是最新。

## 打分口径（0-100）

**必选门槛**：标题/摘要里必须有「发放动作」（领取/立减/券/免费/买一送一…）。
没有就是讨论帖、新闻、交易帖，直接排除——这一条挡掉了 NodeSeek 的
「收/出」二手帖和蓝点网的科技新闻。

**硬排除**：已结束（已领完/已开奖…）、交易（收/出/求购）、抽奖（概率性）、
新闻（确认/发布/漏洞…）、讨论（请教/有没有/求推荐…）、
**VPS/主机类**（2026-10-24：分类为「服务器 VPS」或标题带 vps/独服/小鸡/cn2 等黑话，整体排除）、
**梯子/机场**（梯子|翻墙|机场订阅|clash|v2ray|trojan|vpn…；注意「机场贵宾厅」这类
生活羊毛不误伤——只命中带推广语境的组合词）、
**AI 中转站**（第三方倒卖 API；大厂官网白名单 `OFFICIAL_AI_DOMAINS` 优先放行）、
**非科技题材**（2026-10-24 用户定，见下节）。
意图类规则只看**标题**：摘要是发帖人的描述文字，常含「看看有没有…」，
按标题+摘要判会把真福利误杀（实测：四川移动网龄福利）。

### 只做科技题材（2026-10-24 用户定）

**吃的、饮料、生活日用品、服饰美妆、家电、购物券/满减/年卡充值/话费流量 一律不发**，
只保留科技相关：AI 官方额度、软件/游戏限免、云资源与域名建站、数码硬件本身的资讯。
判据在 `wool_policy.py` 的 `NONTECH_RULES` + `TECH_MARK` + `tech_verdict()`，
输出归因「非科技·吃的/生活用品/服饰美妆/家电/购物券/影音会员/无科技特征/购物帖」。

判定顺序与两个关键取舍：

1. **先看消费词，但科技词可豁免**。`赛博领鸡蛋` 是「领福利」黑话（不是真发鸡蛋）、
   `ChatGPT 送 1 个月会员` 是科技福利——它们命中消费词但带科技词，正常放行。
2. **`购物券` 与 `影音会员` 不可豁免**。`1099→543 国补直降：华为 WATCH FIT 5`
   带「智能手表」、「咪咕游戏VIP」带「游戏」，但本质是电商打折和影音会员，
   照样排除（`NONTECH_HARD`）。
3. 科技词 + 强促销语（券后/凑单/低至/到手价）且**没有发放动作** → 「购物帖」排除。
   `腾讯轻量云秒杀` 这类云资源促销不在此列（秒杀允许科技词豁免）。

**加权**：免费/可领 +25，入口清晰 +15，永久 +10，说明详细 +10，官方域名 +8，
今日新增 +20，昨日 +12。
**减权**：付费前置 −15，满减门槛 −8，限地区 −12，限银行卡/运营商 −6，
含推广词 −25，教程向 −10。

**确定性标签**：确定 / 需满足条件（限地区/银行/号段/付费） / 概率性。

## 与论坛发帖的互通（2026-10-24 起，方案二）

- **已发过的不再推荐**：每轮生成前读发帖台账（baipiao-daily skill 的
  `data/posted.jsonl`），URL 或标题对得上的直接剔除（排除区归因「已发帖」）。
  识别字段是 `src_url`——draft.py 生成的骨架头部带 `<!-- wool: url=… -->` 溯源注释，
  forum_api.py 发帖记账时提取；老条目（无 src_url）用归一化标题兜底。
- **发帖侧反向消费**：baipiao-daily 的 `fetch_sources.py --from-wool` 直接读
  `data/日期.json` 当候选池（本表每晚已抓全部源），只补抓 10 个**快变源**
  （TG 频道/当日限免/当日生活羊毛）保新鲜，其余源隔夜不丢内容不重抓。
- 抓取层已合并：本脚本 import skill 的 `fetch_sources.py`（23 源一份清单一份代码）。
- 打分口径也已合并（2026-10-24）：分类/标记/打分/硬排除的唯一出处是
  `skill/scripts/wool_policy.py`，本脚本与 fetch_sources.py 都 import 它——
  **改口径只改那一个文件**，候选卡和推荐表自动同步。

## 定时任务

Hermes cron `3c67d418c73f`（名称「羊毛日报网站更新」），每天 **9/15/21 点**
（`0 9,15,21 * * *`），**no-agent 模式**——脚本 stdout 直接投递，零 token：

1. 跑 `~/.hermes/scripts/wool-daily.sh`：`git pull` 同步远端 → `wool_daily.py` 生成 →
   `cp` 到 `index.html` 与 `YYYY-MM-DD.html` → `git commit` + `git push` 发到 GitHub Pages
2. 消息写进临时文件 `MSGFILE`，块外的 `cat` 打到 **stdout**，由 cron 的 `deliver=qqbot` 投递

**没有 AI 点评了**（2026-10-24 v3 起），也不再推 QQ 附件。

改动定时：`hermes cron edit 3c67d418c73f …`。
日志：`~/.hermes/logs/wool-daily.log`；每轮输出：`~/.hermes/cron/output/3c67d418c73f/`。

### 推送通道

| 内容 | 通道 |
|---|---|
| 推荐表 | GitHub Pages（`git push` 到 `xiaopeng66/wool-daily`，仓库根 `index.html` = 最新） |
| 通知 | **cron `deliver: qqbot`**（脚本 stdout 即最终消息）。生成失败时脚本 `exit 2`，cron 发失败告警 |

**为什么从微信换成 QQ，又为什么改回「cron 投递」**（2026-10-24 v4 → v5）：

- 微信通道（iLink）有**限流**：2026-10-24 21:00 实测返回 `ret=-2 prepare failed`，
  适配器内部重试 4 次（每次退避 4.5 秒）全部失败，日报生成并发布了但**没收到提示**；
  近 25 次投递里失败 5 次，全是这个 `ret=-2`。
- v4 曾让脚本内直调 `qqbot-send-file.py`，结果和 cron 的 `deliver=qqbot` **叠加，发了两条**。
  v5 起只保留 cron 一条通道，脚本只负责把消息写到 stdout —— 通道单一、内容统一从这里出。
- 微信文件通道还有假成功 bug（`_send_file` 不检查 ret 码），这也是 10-19 就停用微信附件的原因。
- `qqbot-send-file.py` 仍保留，用于**手动补发**（`python qqbot-send-file.py --text "…"`），日常不走它。

注意：cron 实际跑的是 `~/.hermes/scripts/wool-daily.sh`（部署副本），项目内的
`run-daily.sh` 是它的源。**改完必须复制过去，否则改的是个不跑的副本**——
2026-10-26 就踩过：工作区还停在 v4，WSL 侧早已是 v5。

```bash
cp run-daily.sh ~/.hermes/scripts/wool-daily.sh && chmod +x ~/.hermes/scripts/wool-daily.sh
diff -u ~/.hermes/scripts/wool-daily.sh run-daily.sh   # 应无输出
```

## 已知限制

- 抓取失败**会自动重试 3 次**；仍失败时报告顶部会显示红色告警条（写明哪个源缺失），
  不会静默变成一张空表（实测 2026-10-18 一次 jike 超时把 13 条打成 1 条，才加的这层）。
- 截止日/有效期不做自动核验，"已结束"只靠标题关键词，写稿前仍要点开原帖确认。
- 分数只用于排序，不代表官方口径；页面里也写明了这一点。
- 简报只取 TOP 8，完整表在 HTML 里。
- 页面里的明文 URL 超过 56 字符会截断显示，但 `href` 是完整链接（按钮可点）。
- **非科技判定靠关键词**，会有边界误判：新出现的商品品类（如某个没收录的品牌名）
  可能漏进推荐区，新出现的黑话可能被误杀。发现后在 `wool_policy.py` 的
  `NONTECH_RULES` / `TECH_MARK` 补词，两处引擎立即同步。
- **台账 `seen.json` 只增不减**：某条今天被展示过、后来又被新口径排除，它的
  `first_seen_day` 仍记为今天。这不影响判据（明天起按「往期未选」正常沉底），
  只是 `shown` 计数会略高于实际入表次数。
